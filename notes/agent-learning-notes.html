📦 LangChain 核心概念

概念简单解释一句话理解
LangChainLLM 应用组件工具箱不是 Agent 本身，更像搭 Agent 的积木盒
Model接入的大模型本体模型负责思考，但不会自动完成整个流程
Prompt给模型的指令模板就像给模型写操作说明书
Message统一管理 system/user/assistant 消息模型看到的上下文载体

Output Parser把模型输出整理成结构化结果把胡言乱语变成程序能读的格式
Agent能决定要不要调工具、怎么继续推进的执行体不只是回答问题，会自己决定下一步

第 2 章

ToolCall：从文本触及现实

Agent 诞生的最开端——模型从输出字符串，到调用工具的蜕变

核心本质：模型接受字符串，输出字符串。对 AI 所有能力的开发，都在这串字符串上。会调用工具的模型，就已经可以称为最基础的 Agent。

最简单的 ToolCall 原理：

get_weather:Beijing → 解析函数名和参数 → 调用对应函数

实际流程三步走：

1.
获取模型输出
从 model.output 拿到字符串，按预定格式解析
2.
提取工具调用
通过字符串提取，找到实际编写工具逻辑的函数
3.
执行并返回
调用对应函数，将工具输出返回给模型

Chatbot → ToolCall 这一步，是 AI 从"被动对话"到"主动影响现实"的范式跃迁。有了它，AI 不再只是回答问题，而是能动手做事。

第 3 章

Agent Loop：从做一步到做一件事

Agent 的起点不是工具，而是"循环"

单次 ToolCall 只能完成单一目标的简单任务。为了扩展 Agent 能力，引入 Agent Loop，让它能自动完成更复杂的任务。

🔄 ReAct — 摸着石头过河

Think ⇄ Act → End

ReAct 是一个三节点循环：模型先思考 → 决定调什么工具 → 执行工具看结果 → 再决定下一步 → 直到结束。最关键的贡献是将大模型变成了一个 状态机，内部维护 Message State（消息列表），不断追加 Think 和 Act 的结果。

模式核心思想角色数上下文压力适用场景
ReAct走一步看一步，摸着石头过河1 个🔴 极高简单单次工具调用、信息检索
Reflection左脚踩右脚上天，自我挑刺修正2 个（生成者+审查者）🟡 中高写代码、翻译、长文章
Plan-and-Execute包工头与干饭机器，全局拆解按图索骥2-3 个🟢 较低长程任务、数据分析、开发小游戏

Reflection 在 ReAct 里多加入一个 Critic 节点专门负责审查，防止单一 ReAct 的幻觉。

Plan-and-Execute 解决长任务中 ReAct 的"短视"和"遗忘"问题：
Planner（规划者）写出详尽的 Task List → Executor（执行者）专心执行 → Replanner（复盘者）更新计划。

三种模式的核心区别：ReAct 用一个模型既当爹又当妈（全部塞在一个上下文里）；Reflection 引入专门审查者互相制衡；Plan-and-Execute 把"想"和"做"彻底拆开，降低上下文压力。越复杂的任务，越需要拆分。

第 4 章

MultiAgent：众人拾柴火焰高

单 Agent 的能力是有极限的

Plan-and-Execute 解决了"长任务拆解"问题，但 Executor 往往还是同一个大模型，既要会写前端又要会写后端，能力被摊薄。MultiAgent 将多个不同能力的专家集合进行分工，类似模型架构里的 MoE（混合专家）。

🔑
Router 规则清晰
合理安排任务给对应专家
🔑
Expert 领域明确
每个执行者负责的领域清晰、对应能力强
复杂度到这个层级，需要考虑的就是工程化的问题了。
第 5 章

Engineering：真正成熟的关键一步

Agent 从"能做"到"能可靠做"，中间差的是工程化

📖 Context Engineer

术语由 Shopify CEO Tobi Lutke 在 2025 年 6 月提出，被 Karpathy 转发，阅读量 210 万次。它比"提示词工程"更贴切地描述了向 LLM 提供全面背景信息的技能。

核心思想 — 四大操作

  • 写入（Write） — 把会话关键内容即时保存到上下文窗口之外，如 CLAUDE.md、PLANNING.md、记事板
  • 选择（Select） — 按需拉取最相关的内容到上下文，工具通过 RAG 挑选，记忆通过 embedding 检索
  • 压缩（Compress） — 上下文总结 + 剪裁，如 Claude Code 的 auto-compact 在达到 95% 窗口时自动总结
  • 隔离（Isolate） — 多 Agent 各自独立上下文窗口，沙箱环境隔离，状态对象隔离

工程方法 — 九种策略

  • Notepad / TODO 短期记忆
  • 工程约束文件（CLAUDE.md 等）
  • 压缩机制（优先丢可再取的）
  • 动态工具选择（规则筛选+top-k）
  • 动态 Prompt 组装（base+mode+domain+memory）
  • 路径作用域规则
  • 结构化输出全面化
  • 分层记忆（rules / working memory / history）
  • Skills / references 按需加载

🎛️ Harness Engineer

如果说 Context Engineer 解决的是"模型此刻看到了什么"，那么 Harness Engineer 解决的就是"模型此刻在什么环境里工作、能做什么、怎么被约束、怎么恢复、怎么被观察"。

📦
启动（Provision）
隔离工作区、沙箱环境、工具网关
⛔
控制（Gate）
Human Review、Guardrails、权限边界
💾
保存（Persist）
Checkpoint、Resume、Run State
📡
观测（Observe）
Tracing、Logs/Metrics、测试反馈
🧱
约束（Enforce）
AGENTS.md 路由、Linters、规则前置
🧩
隔离（Isolate）
Subagents、Worktree、State Isolation
Context Engineer 的隔离 → 隔离"上下文噪声"
Harness Engineer 的隔离 → 隔离"运行时副作用"

Context Engineer 和 Harness Engineer 是一个问题的两面：一个管"信息环境"，一个管"运行环境"。两者缺一不可。Agent 到了生产阶段，不能只在 prompt 上下功夫，还要在运行时架构上做文章。

第 6 章

Skill：把能力变成可复用资产

Skill = 面向 Agent 的可复用工作流包

它不是单个工具，也不是完整 Agent，而是把一类任务的步骤、知识、脚本和检查点封装起来，供 Agent 在合适时机调用。通常是一个文件夹 + SKILL.md 清单 + 可选脚本/参考资料。

my-skill/ ├── SKILL.md ├── scripts/ │ └── run.py ├── references/ │ └── REFERENCE.md └── assets/ └── template.md
工程化完善后，最终一定是产品化，触及非技术人员。
第 7 章

Claw：交互与产品化落地

Agent 不再是工程师专属，产品化的时代来了

2026 年，OpenClaw 爆火（361k stars，73.6k forks，GitHub Star 第一单体项目）。最大贡献是告诉所有人：Agent 时代早已不是程序员工程师的范围，在所有工程化的铺垫下，Agent 现在可以套上交互层，普及到普通用户。

OpenClaw 的爆火揭示了一个趋势：未来 Agent 开发不能只盯着"能力"，还必须盯着"可用性"。谁把交互层做得更简单明了，谁就更接近真正的产品。

🧩

产品思维

技术能力决定了你能做什么，产品思维决定了你应该做什么

🎁

学会包装

同样的技术实现，不同的呈现方式带来截然不同的感受

🤝

人的连接

沟通、共情、理解需求——超脱于技术之外的核心价值

传统软件工程经验没有过时——测试驱动开发变成 Agent 自检机制，架构设计变成多 Agent 分工，错误处理变成兜底策略，版本管理变成 Prompt 版本化。不要因为 AI 的存在就放弃工程基础，恰恰相反，工程基础决定了你能不能把 AI 用好。
